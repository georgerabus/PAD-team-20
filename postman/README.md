# Server Rules and University Record Postman collections

These two collections exercise the local Laravel lab implementations, including their explicitly documented mocks:

| Collection | Default base URL | Requests |
|---|---|---|
| `server-rules.postman_collection.json` | `http://127.0.0.1:8001` | 37 |
| `university-record.postman_collection.json` | `http://127.0.0.1:8002` | 41 |

Existing teammate collections in this directory are unchanged. Their authentication/setup differs; the instructions below apply only to these two Laravel collections.

## Import and run

1. Start both Laravel services from their endpoint implementation branches, with dependencies installed and migrations applied. Keep each terminal open. Docker is not required for this step.
2. In the **Postman desktop app**, choose **Import** and select both `.postman_collection.json` files.
3. No separate environment is needed. Each collection contains its own default URLs and public lab token variables. If you use another port, edit `rulesBaseUrl` or `recordsBaseUrl` in that collection's variables.
4. Open a collection, choose **Run**, keep every request selected and in its original order, and run one iteration.
5. All assertions should pass. Requests named Reject, Deny, or Authentication required intentionally expect errors. A 401/403/422 response alone is not a failed collection test; an incorrect status or response shape is.

For an individual request, execute the preceding setup requests first. The Rules collection's first two requests capture base and current rule versions; University Record's first request captures applicantId. There is no need to manually paste IDs.

Do not create environment variables named `rulesVersion`, `baseVersion`, `otherVersion`, `applicantId`, their `Snapshot` variants, `missingRulesSession`, or `missingApplicantId`; they would shadow values generated by the collection. Avoid other same-name environment overrides unless intentional. If you choose to run requests one at a time outside Runner, keep their original order.

## Service configuration

Both services need `APP_ENV=local` and `MOCK_AUTH_ENABLED=true`. University Record also needs `MOCK_BOOTSTRAP_ENABLED=true`. Use the service repositories' `.env.example` as the starting point; do not commit private `.env` files.

Both collections assume the configured mock player session is:

```text
11111111-1111-4111-8111-111111111111
```

University's other-session fixture is `22222222-2222-4222-8222-222222222222`. Collection variables must match the corresponding service configuration.

Server Rules tokens: `lab-session-service`, `lab-moderation-service`, `lab-player`.
University Record tokens: `lab-session-service` and the `lab-records-*` fixtures documented in its service README. These are intentionally public test fixtures, **not real credentials or JWTs**. These collections are not a test of real issuer signing, Session integration, RabbitMQ delivery, or the full eight-service Docker stack. They do not use the team's `SERVICE_SECRET`.

Both collections check the **current local lab policy**, including the level-5 rules and the University Record reference fixtures. If the team agrees different rule/channel/record policies, update the matching assertions with those service changes. Academic year 2026/autumn and the September 24 sample message timestamp are fixture values, not assertions about the current date.

## Covered behavior

Server Rules:

- Create level-0 and level-5 rule sets; capture generated versions.
- Read current and historical versions and compare exact stored snapshots.
- Evaluate accept, restricted-channel acceptance, flag, reject, ban, and severity precedence.
- Match violation IDs to the actual rules created in that run.
- Check invalid tokens, wrong service callers, invalid UUIDs/levels/subject fields, obsolete request format, missing resources, malformed JSON/content type, and session isolation.

University Record:

- Materialize one mocked ApplicantInitialized payload and repeat it to check the same applicant ID is returned.
- Read every assigned record and reference endpoint; verify exact lab response shapes/data.
- Deny each per-applicant record for an unassigned token and for another session.
- Gate courses, allow academic-year without assignment, and reject query-string permission spoofing.
- Check missing/invalid authentication, validation failures, absent applicants, public ground-truth injection, malformed JSON/content type, and the removed ground-truth route.

The replay HTTP assertion checks stable identity. The service's PHP tests also verify that replay does not overwrite saved ground truth and that a failed event receipt rolls back the transaction.

## Database effects and repeat runs

The Server Rules collection creates **three new versions per iteration**. It deliberately does not delete them because the contract has no deletion endpoint. The University Record collection creates at most one fixture applicant for its configured session and replays it thereafter. Run against a development database. Negative requests must not create application records.

Generated IDs are reset and captured at the beginning of each run, so rerunning does not assume a fresh database or version 1. Missing-version tests use `2147483647`, which must remain unused in your lab database. Missing applicant/session checks generate random UUIDs.

## Optional command-line verification

Postman desktop is enough for the assignment. Newman provides another way to run these v2.1 collections. From the common repository root, with Node.js/npm available:

```cmd
npx --yes newman@6.2.2 run postman/server-rules.postman_collection.json
npx --yes newman@6.2.2 run postman/university-record.postman_collection.json
```

To test on different ports, append `--env-var rulesBaseUrl=http://127.0.0.1:PORT` or `--env-var recordsBaseUrl=http://127.0.0.1:PORT` respectively. No build/run automation script or database-population script is included.

Official documentation: [Newman collection runner](https://learning.postman.com/docs/reference/newman-cli/command-line-integration-with-newman) and [collection v2.1 schema](https://schema.getpostman.com/json/collection/v2.1.0/collection.json).

## Integration workflow

This task adds collections only; it does not merge service implementation PRs, update submodule references, or change the communication contract. The collection changes belong on `chore/postman-collections`, reviewed through a PR against the common repository's `dev`. Add the real project-board task link to the PR when available.

After Postman: build/publish public Docker images for both `linux/amd64` and `linux/arm64`, verify the manifests, connect each service to its own PostgreSQL container and named volume, then extend the shared image-based Compose configuration and documentation. Docker packaging remains a separate task.
